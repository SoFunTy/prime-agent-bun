# 会话记录分析：Bun 内核 vs Python 内核

数据来源：本机 `~/.prime/agent/sessions/*.jsonl`（**真实会话，非合成基准**）。
分析脚本：`python3 scripts/fork/kernel_session_stats.py`（本文所有数字都由它输出）。

## 0. 结论先行

| 问题 | 会话记录给出的答案 |
| --- | --- |
| 内核替换让单元格更快了吗？ | 同口径（相同命令）**没有**：29.0ms vs 31.5ms，Cliff's δ=-0.03（≈0） |
| 全语料能省多少时间？ | 反算上界 **≈8 秒**（8,700 格、几个月）；按同口径命令算是 **-22 秒**（Bun 略慢），净效果在噪声内 |
| 哪里确实更好？ | `import` 5→1ms、`await` 15→5ms、内核就绪 21→14ms（p90 115→23ms，max 4.5s→33ms） |
| 哪里变差了？ | 错误率 2.3%→4.0%（语言迁移），负载下内存更高 |
| 真正让对话变快的是什么？ | 旧 daemon 换掉 + provider 代理绕过：35–45s/轮 → **2.2–2.8s/轮**（约 14×） |

一句话：**内核替换是基础设施层面的收益（去掉 235MB venv、启动更稳），不是端到端加速。**

## 1. 口径与方法

- 单元格 = `toolResult`，工具名属于内核别名（`python_repl`/`bun_repl`/…），耗时取 `details.durationMs`。
- 分类：`bash_trivial`（单条 echo/pwd/true）、`bash_other`、`file_or_net`、`import`、`await`、`wait`（sleep/setTimeout）、`pure_short`（≤2 行）、`pure_multi`。
- 统计：中位数、p75/p90/p95/p99、均值、标准差、变异系数（CV）。
- 不确定性：中位数的 **session 级 cluster bootstrap 95% 置信区间**（按会话重采样，避免单会话主导）；错误率的 **Wilson 95% CI**；匹配队列的 **Cliff's delta**（正 = Bun 更慢）。
- 唯一严格同口径：**单条 bash 命令且命令字符串完全相同**。其余分了类别/分桶，只作上下文。

## 2. 语料概况

| | Python 内核 | Bun 内核 |
| --- | ---: | ---: |
| 会话数 | 48 | 7 |
| 内核单元格 | 8,700 | ≈425 |
| 每会话单元格（均值） | 181.2 | 60.7 |
| 单元格总耗时 | 517.8 min | 38.0 min |
| 时间范围 | 2026-10-23 → 11-10 | 2026-11-11（单日） |
| 主要模型 | `commandcode/deepseek-v4.1-flash` 4,623；`-fast` 2,511；`glm-5.3-flash` 807 | `deepseek-v4.1-flash` 420；`glm-5.3-flash` 5 |

两份语料**不是同一份工作**：Bun 侧基本是一个 Nuxt/CloudBase 重活会话（安装、构建、网络、刻意等待），Python 侧是几个月的混合工作。它们唯一重叠的模型是 `deepseek-v4.1-flash`，这也让第 7 节可以做模型控制对比。

## 5. 严格同口径：相同命令

单条 bash 命令、命令字符串完全一致的单元格：

| 命令 | Python n / 中位 | Bun n / 中位 |
| --- | ---: | ---: |
| `bun test test/ 2>&1 \| tail -3` | 8 / 20.5 | 2 / 30.0 |
| `bun test test/ 2>&1 \| tail -4` | 2 / 24.5 | 7 / 47.0 |
| `bun test test/ 2>&1 \| tail -5` | 2 / 2,576.5 | 2 / 32.0 |
| `bun test test/ 2>&1 \| tail -6` | 3 / 52.0 | 4 / 27.5 |
| `bun test test/ 2>&1 \| tail -8` | 5 / 51.0 | 1 / 30.0 |
| `ls -la` | 3 / 37.0 | 2 / 15.5 |
| **合计** | **23 / 29.0** | **18 / 31.5** |

Cliff's δ = **-0.03**（≈ 无差异）。单元格耗时主要是子进程启动与命令本身，解释器开销占比很小。

## 7. 模型控制：同一个 provider/model 下对比

| model | Python n / 中位 | Bun n / 中位 |
| --- | ---: | ---: |
| `commandcode/deepseek/deepseek-v4.1-flash` | 4,623 / 55.0 ms | 420 / 46.5 ms |
| `commandcode/z-ai/glm-5.3-flash` | 807 / 44.0 ms | 5 / 12.0 ms |

同模型下 Bun 中位低 15.5%，但**仍然混着工作差异**（Bun 那 420 格几乎都来自同一个重活会话）。
`glm` 的 Bun 样本只有 5 格，不可用。这个 -15.5% 只能当上界看，不能当内核结论。

## 8. 错误率与错误类型

| kernel | 错误 / 总数 | 比率 | 95% Wilson CI | 主要错误 |
| --- | ---: | ---: | ---: | --- |
| python | 204 / 8,700 | 2.3% | [2.0%, 2.7%] | SyntaxError×32, FileNotFoundError×29, TypeError×23, AttributeError×22 |
| bun | 17 / 425 | 4.0% | [2.5%, 6.3%] | SyntaxError×8, ReferenceError×2, KeyboardInterrupt×2 |

Python 侧 204 个错误里 182 个是“代码本身写错”（语法/类型/文件），Bun 侧的 `SyntaxError`/`ReferenceError` 集中在切换初期的语言混淆（把 Python 写进 JS 内核）。这是会话记录里**唯一显著变差的指标**；prompt 层与卡片分发修复针对它，续接旧 Python 会话仍会复发。

## 9. 内核就绪（每会话第一个单元格）

| python | 48 | 21.0 ms | 115.0 ms | 4,476.0 ms |

Bun 的 7 个会话里多数是小型验证会话（中位 1 格），这进一步说明样本不代表日常负载。

## 13. 反算：全语料到底省多少

- **严格同口径（相同命令）**：+2.5 ms/格（Bun 更慢）；若把 8,700 个 Python 格全换成 Bun，**+21.8 秒**（更慢）。
- **宽松上界**：把 `import`（+4.0ms × 381）与 `await`（+10.0ms × 640）的差全算作收益，合计 **+7.9 秒**。
- 两个口径互相矛盾（一个更慢、一个略快），说明差异在噪声内。**净效果 ≈ 0，绝对量 < 20 秒 / 8,700 格 / 几个月。**

## 14. 会话记录里真正的提速

同一 provider（commandcode / `z-ai/glm-5.3-flash`）、同类提问，前后对比：

| 状态 | 轮次耗时 | 失败 |
| --- | ---: | --- |
| 旧 daemon（0.10.1）+ 系统代理 | **35.0s / 44.7s** | 每轮 1–2 次 `Connection error.` |
| fork daemon + `bypassProxy` | **2.82s / 2.20s** | 0 |

约 **14×**。`PI_REQUEST_TIMING=1` 的首字节实测也一致：走代理 9.6s → 绕过 1.9s。这部分收益属于 **daemon 清理 + 代理绕过**，与内核无关。

## 15. 结论

1. 会话记录**不支持**“换 Bun 内核让 agent 更快”的说法；同口径下没有差异，反算净效果 < 20 秒。
2. 内核替换的真实收益：`import`/`await` 少 4–10ms、内核就绪更稳（max 4.5s→33ms）、去掉 235MB Python venv、空闲内存更低。
3. 真实变差项：错误率 2.3%→4.0%（语言迁移），负载下内存更高。
4. 端到端提速请归因给：旧 daemon 清理（否则 TUI 跑在 0.10.1 worker 上）+ provider `bypassProxy`。
