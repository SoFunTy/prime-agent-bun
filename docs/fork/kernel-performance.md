# 会话记录分析：Bun 内核 vs Python 内核

数据来源：本机 `~/.prime/agent/sessions/*.jsonl`（**真实会话，非合成基准**）。
分析脚本：`python3 scripts/fork/kernel_session_stats.py`（本文所有数字都由它输出）。

> 快照时间：2026-11-11。语料随使用增长；同一指标在不同快照间可能变号（见 §5 的说明），
> 这正是“差异很小”的证据。

## 1. 对比值总表（先看这张）

`Δ = Bun − Python`；比例 `<1` 表示 Bun 更快；变化率负数表示 Bun 更快。

**内核就绪**（p90 0.20×、max 0.01×）和**错误率**（1.55×，变差）。

## 2. 口径与方法

- 单元格 = `toolResult`，工具名属于内核别名（`python_repl`/`bun_repl`/…），耗时取 `details.durationMs`。
- 分类：`bash_trivial`（单条 echo/pwd/true）、`bash_other`、`file_or_net`、`import`、`await`、`wait`（sleep/setTimeout）、`pure_short`（≤2 行）、`pure_multi`。
- 对比值：中位数、Δ、倍数、百分比变化。
- 不确定性：中位数的 **session 级 cluster bootstrap 95% CI**（按会话重采样）；差值 CI（两个内核各自重采样后取中位差）；错误率 **Wilson 95% CI**；匹配队列 **Cliff's delta**（正 = Bun 更慢）。
- 唯一严格同口径：**单条 bash 命令且命令字符串完全相同**。其余分桶/分类只作上下文。

## 14. 会话记录里真正的提速

同一 provider（commandcode / `z-ai/glm-5.3-flash`）、同类提问，前后对比：

| 状态 | 轮次耗时 | 失败 | 对比值 |
| --- | ---: | --- | ---: |
| 旧 daemon（0.10.1）+ 系统代理 | 35.0s / 44.7s | 每轮 1–2 次 `Connection error.` | — |
| fork daemon + `bypassProxy` | 2.82s / 2.20s | 0 | **0.06× / -94%** |

约 **14×**。`PI_REQUEST_TIMING=1` 的首字节实测一致：走代理 9.6s → 绕过 1.9s（0.20×）。
这部分收益属于 **daemon 清理 + 代理绕过**，与内核无关。

## 15. 结论

1. 严格同口径的对比值是 **0.89× / -10.8%**（Bun 略快），但 **CI 跨 0、Cliff's δ=-0.17**，且随快照变号——统计上不可区分。
2. 稳定的对比值只有两类：**内核就绪**（p90 0.20×、max 0.01×）和 **`import`/`await`**（0.20×/0.30×）。
3. 变差项：**错误率 1.55×（+1.3 pp）**，负载下内存更高。
4. 反算净效果 **-244s 到 +61s / 8,700 格 / 几个月**，不是端到端提速。
5. 端到端 14× 的提速归因于：旧 daemon 清理 + provider `bypassProxy`。
